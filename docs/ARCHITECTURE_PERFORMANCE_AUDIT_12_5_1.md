# VoiSee 12.5.1: аудит устойчивости, ресурсов и архитектуры

Дата: 31 октября 2026. База анализа: `b1829bb` (поставка 12.5.1; исходники релиза — `685bea1`). Текущая `main` не переключалась. Изменения 13.x рассматривались отдельно и не приняты за рабочую основу.

## 1. Что проверено и насколько достоверны выводы

Проверены жизненный цикл движка и устройств, потоки capture/render, DSP, шумоподавление, кеш/декодирование, SoundBoard, Media Bridge, фоновые задачи, сцены, горячие клавиши, таймеры, хранение файлов и сборка/упаковка.

Для замеров из Git извлечены неизменённые исходники аудиобиблиотеки 12.5.1. Собран отдельный Release console harness, не открывающий микрофон, аудиовыходы или пользовательские настройки. Для проверки файловой операции также подключены исходные SoundBoardLibraryStore/модели, а StartupLog заменён пустым тестовым адаптером. В тестах используются только синтетические WAV и временные данные внутри `artifacts/audit-12.5.1`.

Машина: Intel Core i7-14650HX, 24 логических процессора; Windows 10.0.26200, .NET 8.0.28. Для воспроизводимости измеряемого DSP tiered compilation отключён; результаты не эквивалентны профилю холодного запуска приложения. Тайминги — один локальный прогон, не статистическая гарантия. Квантизация Process.TotalProcessorTime особенно заметна в коротких тестах.

Различаются три вида свидетельств:

- **Замер / воспроизведение:** результат исполнения исходных компонентов на синтетических данных.
- **Подтверждено кодом:** механизм и недостаток видны в реализации, но конкретный сбой устройства или системы не воспроизводился.
- **Гипотеза для профилирования:** влияние зависит от оборудования, размера библиотеки и сценария.

**Полный профиль WinUI-приложения с устройствами и пользовательской библиотекой не измерен.** На момент начала аудита процесса VoiSee не было. Дополнительно собрана изолированная диагностическая копия оболочки 12.5.1 и измерен её idle-режим; условия приведены ниже. Ни цифры консольного стенда, ни размер установщика нельзя называть потреблением RAM всего приложения. Не выполнены длительный live soak, физический loopback, отключение USB/BT-устройств, проверка сна/пробуждения, дампы реальных падений, GPU trace и энергопрофиль. Для доказательства отсутствия утечек и оценки нагрузки в рабочих сценариях эти проверки обязательны.

Результаты сохранены в `docs/audits/2026-10-31/`; исходный стенд и извлечённая база — в `artifacts/audit-12.5.1/`.

## 2. Измеренная память

### Оболочка WinUI в простое

Из коммита b1829bb собрана отдельная диагностическая копия: пустые изолированные settings/library, автозапуск engine отключён, Discord mute отключён, запуск `--background` в трей, автоматический штатный выход через 35 секунд. Изменены только пути/защитные условия запуска и таймер выхода; production-дерево не менялось. Release-сборка прошла без ошибок и предупреждений с локальным NuGet source.

Снято 70 process samples с шагом 500 мс; 39 samples между 10-й и 30-й секундами использованы для steady-state:

| Метрика | Результат |
|---|---:|
| Средний Working Set | 185,45 МиБ |
| Средний Private Bytes | 108,42 МиБ |
| Максимальный Working Set в коротком прогоне | 185,54 МиБ |
| Максимальный Private Bytes | 108,51 МиБ |
| CPU в эквиваленте одного ядра | 1,60% |
| Завершение | штатное, exit code 0 |

На 24 логических CPU это около 0,067% от суммарной вычислительной ёмкости, но показания конкретного Task Manager могут округляться/нормализоваться иначе. Working Set и Private Bytes не складываются. Режим не включает показ/перерисовку активного окна, реальный audio engine, Discord polling и библиотеку пользователя, поэтому это ориентир базовой стоимости оболочки, а не гарантированный minimum или полный профиль stock-приложения.

При первоначальном запуске оболочка попыталась выполнить штатный autostart refresh/repair; доступ к registry был запрещён окружением, ошибка обработана приложением. Изменений registry не произошло. Эта одноразовая попытка была до измеряемого интервала. В сохранённый prepare-ui.py дополнительно добавлен явный запрет repair в диагностической копии для безопасного повторения теста.

### PCM-кеш — главный подтверждённый источник неограниченного роста

SoundFileLoader хранит полные float[] в static ConcurrentDictionary. Ключ содержит путь, время модификации, частоту и число каналов. Лимита по байтам, TTL, LRU и автоматического удаления старых ревизий нет. MainWindow.WarmSoundCacheInBackground заранее загружает всю библиотеку при старте движка.

Внутренний формат 48 000 × 2 × 4 = **384 000 байт/сек**, то есть **21,97 МиБ/мин**:

| Длительность загруженного аудио | Только PCM, без UI/runtime/native |
|---|---:|
| 1 минута | 21,97 МиБ |
| 3 минуты | 65,92 МиБ |
| 10 минут | 219,73 МиБ |
| 100 минут | 2197,27 МиБ ≈ 2,15 ГиБ |

Это расчёт для фактически загруженной суммарной длительности, а не для всех пользователей. Размер MP3/OGG на диске эту величину не ограничивает.

**Замер:** три разных WAV по 60 секунд после полной GC удерживают **65,919 МиБ**. Их создание/декодирование/загрузка суммарно выделили **207,683 МиБ** управляемой памяти; это суммарные allocations, а не измеренный пиковый Working Set. После ClearCache и GC осталось менее 0,01 МиБ сверх контрольного уровня. Проблема — политика удержания, а не доказанная неисправность GC.

Причины временного расхода: декодирование через растущий List<float>, увеличение его capacity и завершающий ToArray. Редактор дополнительно создаёт копию выделенного диапазона; preview и промежуточные версии могут одновременно удерживать исходный кеш, edited[] и другие массивы.

**Решение:** один общий бюджет кеша в байтах; короткие часто используемые звуки — LRU с учётом активных ссылок; длинные треки/фон — потоковый decoder с ограниченным read-ahead; отменяемый последовательный prefetch только ближайших звуков. Для редактора — отдельный ограниченный working set и обработка файла блоками. Повторно используемый блок нельзя возвращать в pool, пока его читает транспорт.

### Выделения в аудиоколбэке

SoundboardTransport.MixSound делает `new float[count]` на каждый звук и выход. В тесте блок — 20 мс, stereo; оба выхода читаются синхронно, используется один общий PCM-файл и несколько независимых активных playback keys.

| Активных звуков | Выделения на 20 мс, оба выхода | Пересчёт на секунду аудио |
|---:|---:|---:|
| 1 | 15 408 байт | 0,735 МиБ/с |
| 8 | 123 264 байт | 5,878 МиБ/с |
| 32 | 493 056 байт | 23,511 МиБ/с |

Это нагрузка на allocator/GC, не постоянное удержание такого объёма каждую секунду. Тем не менее GC-паузы и конкуренция потоков могут проявляться щелчками даже при небольшом среднем CPU.

AudioFormatConverter также выделяет новый выходной массив на каждый блок, а PcmFloatConverter создаёт входной. Отдельно измеренная стадия преобразования float[] 48k stereo выделяет около **7704 байт/20 мс**; эта цифра не включает предварительное преобразование byte[] capture.

**Решение:** заранее выделенные буферы и Process/Read в предоставленный Span; микширование непосредственно в destination; фиксированные кольцевые очереди. В штатной steady-state обработке не должно быть файлового I/O, декодирования, расширения коллекций и ожидания UI.

Сам SimpleVoiceProcessor создаёт примерно **0,734 МиБ** управляемых объектов при конструировании; микробенчмарк не показывает существенных постоянных аллокаций внутри его обычного ProcessInPlace. Полный переписыватель DSP ради памяти сейчас менее приоритетен, чем кеш и микшер.

## 3. CPU и другие ресурсы

### DSP и шумоподавление

Каждый обычный эффект проверен отдельно при условной интенсивности 50%, для pitch +5 и formant +3 semitones, на 180 Hz синусе. Среди отдельных эффектов на стенде самым затратным оказался Vocoder: около **0,20 мс на 20 мс** аудио; несколько pitch/formant-эффектов — примерно 0,1–0,14 мс. Это средние офлайн-тайминги без драйвера и конкуренции с игрой. Сумма эффектов, denoiser и render имеет другую стоимость; p95/p99 реального колбэка пока не измерены.

В двух отдельных процессах подан 48k stereo сигнал блоками 20 мс в реальном темпе: 2 секунды прогрева и 5 секунд замера. DLL взяты из portable 12.5.1.

| Компонент | CPU относительно одного ядра | Working Set всего тестового процесса | Private Bytes процесса |
|---|---:|---:|---:|
| RNNoise | 4,05% | 24,08 МиБ | 8,07 МиБ |
| DeepFilterNet | 13,42% | 105,40 МиБ | 49,41 МиБ |

CPU здесь включает стенд и все native worker threads процесса. На 24 логических процессорах это не означает 4%/13% суммарного CPU компьютера. Working Set включает отображённые DLL и общие страницы, Private Bytes измеряет другую величину. Дельта DeepFilterNet относительно контрольной точки составила около +81 МиБ Working Set и +41 МиБ Private Bytes; эти значения чувствительны к JIT и политике ОС.

На запуске DeepFilterNet зарегистрировал одно предупреждение `Underrun detected (RTF: 1.54)`. Максимальное время внешнего ProcessInPlace в замерном интервале — 16,6 мс; у RNNoise — 1,33 мс. Это повод включить startup/underrun-тесты, но не доказательство регулярных срывов на реальном микрофоне.

DeepFilterNet намеренно остаётся загруженным до завершения процесса из-за native worker. После его отключения нельзя ожидать полного возврата памяти как после завершения отдельного процесса. Это известный lifetime, не автоматически бесконечная утечка. RNNoise создаётся даже при выключенном шумоподавлении — можно лениво активировать его после определения корректного жизненного цикла.

### Нагрузка вне DSP

- FloatSampleQueue использует Queue<float> и lock с поэлементным копированием. Оба render-потока и UI могут конкурировать за транспорт. Заменять на кольцевые буферы стоит по измеренному deadline, а не только по среднему CPU.
- В 12.5.1 requested capture/render — 20/50 мс; очереди микрофона и Media Bridge допускают до двух секунд аудио. Это создаёт возможность большой задержки при отставании, а не большой расход RAM сам по себе. Механически снижать WASAPI-буферы без тестов на медленных устройствах нельзя.
- Таймер Media Bridge обновляет UI каждые 50 мс, timeline — каждые 200 мс; Discord sessions опрашиваются каждые 750 мс. Не все обновления прекращаются при сворачивании. Разделить управление и визуализацию: фоновый звук сохраняется, невидимые meters/таймлайны не перерисовываются.
- Превью Media Bridge уже ограничено активной вкладкой и примерно одним кадром в секунду. Его дополнительная стоимость: полноразмерный GDI bitmap окна, уменьшенная копия, PNG encode, передача в WinUI и decode. Для 4K-окна один сырой 32-bit bitmap — около 31,6 МиБ, плюс копии; это расчёт, а не замер live preview. PrintWindow может долго ждать чужой процесс. Нужны лимиты размеров/времени и проверка альтернативного capture-пути.
- На каждое нажатие немодификаторной клавиши hook просматривает библиотеку звуков/пресетов и парсит жесты. При большой коллекции это лишняя работа в чувствительном callback. Нужен предварительно собранный индекс жест → команда и короткая передача события в очередь.
- Сохранение settings и всей библиотеки выполняется синхронно; статистика использования сохраняет библиотеку после успешного запуска звука. Ползунки также вызывают запись. Нужны debounce/batch, один сериализованный writer, ограниченная частота flush и принудительное завершение записи при штатном выходе.
- Лог растёт без лимита в StringBuilder и на диске. При открытом viewer содержимое полностью превращается в строку и назначается TextBlock. Нужны кольцевой буфер, ротация файлов и ограниченное пакетное обновление UI.

## 4. Риски падений и потери данных

Приоритет P1 означает исправление до расширения функциональности. Он не означает, что вылет уже зафиксирован на пользовательском ПК.

| ID / приоритет | Свидетельство и сценарий | Исправление |
|---|---|---|
| R01 / P1 | Подтверждён неограниченный кеш + автоматическая загрузка всей библиотеки; риск OOM на длинных/многочисленных файлах | Бюджет, streaming, лимиты входных файлов, cancellation |
| R02 / P1 | Воспроизведено: чтение только virtual route не завершает one-shot; IsFinished требует `_virtualFinished && _monitorFinished`, статус после 62 с чтения 60-секундного файла всё ещё Active и CurrentSeconds=0 | Учитывать подключённые выходы, общий playback clock; тест отсутствующего monitor |
| R03 / P1 | Подтверждено кодом: Stop/Dispose — последовательная цепочка; исключение одного Stop пропускает дальнейший cleanup. В 12.5.1 `_disposed` устанавливается в конце | Явный state machine, идемпотентный StopAsync, try/finally для каждого ресурса |
| R04 / P1 | ProcessLoopbackCapture.Stop игнорирует результат Join(2s), затем освобождает COM и event; при незавершившемся потоке тот может ещё использовать их | Единственный владелец native-ресурсов; подтверждённый выход worker перед release; timeout переводит в Faulted |
| R05 / P1 | StartMediaBridgeAsync не связан с lifetime/generation движка; pending Start может завершиться после Stop/Dispose | CancellationToken, сериализованное управление, проверка generation перед commit результата |
| R06 / P1 | Запуск/декодирование звука fire-and-forget не отменяется Stop. Поздняя PlaySound может прийти после Stop или нового Play и перезаписать состояние | Очередь команд, sequence ID, отмена загрузки, запрет команд disposed engine |
| R07 / P1 | RecordingStopped сообщает ошибку только в Console; нет согласованного восстановления capture/render и обработчиков PlaybackStopped в основном engine | Running/Faulted/Reconnecting state, device notifications, bounded retry и понятный статус |
| R08 / P1 | Поиск устройств в MainWindow.StartEngine выполняется до try; исключение COM при hot unplug может выйти в UI handler | Обработать всю транзакцию запуска и гарантировать rollback |
| R09 / P1 | Native RNNoise/DeepFilterNet выполняются в процессе UI. Обычный catch не защищает от повреждения памяти native DLL | Crash dumps; сначала исправление lifetime; решение о выделенном AudioHost после проверки IPC и задержек |
| R10 / P1 | SettingsStore/LibraryStore пишут JSON прямо в целевой файл. Ошибка чтения даёт defaults; последующий Save может затереть повреждённый файл | Temp+atomic replace, предыдущая версия, quarantine повреждённого файла, явный результат Save |
| R11 / P1 | ReplaceSoundFile удаляет старый файл до успешного File.Copy нового. Проверено стендом с заблокированным source: IOException и потеря старого файла | Сначала copy/validate во временный файл, затем commit и только потом удаление старого |
| R12 / P2 | AudioDeviceCatalog перечисляет и возвращает MMDevice без явного Dispose для невыбранных и выбранных объектов; engine их также не освобождает | Зафиксировать ownership; детерминированное освобождение. Накопление native handles требует soak-подтверждения |
| R13 / P2 | Сцены не сохраняют EffectOrder; fallback применяет VoiceSliders в KnownVoiceEffectKeys-порядке, именованный пресет связан по имени | Стабильный preset ID + versioned snapshot цепочки |
| R14 / P2 | Старые ревизии кеша могут оставаться после внешнего изменения файла; failed Lazy остаётся в кеше; replace/delete не имеют общей invalidation-политики | Один media catalog/cache service, invalidation транзакцией, retryable failed loads |
| R15 / P2 | В shutdown не останавливаются явно routeRestart и voiceSettingsApply таймеры; фоновые prefetch/preview/анимации не объединены общей отменой | Lifetime scope окна/приложения, Cancel → await → Dispose, запрет callbacks после закрытия |
| R16 / P2 | Большие коллекции UI пересоздаются при выборе/поиске/смене темы; effect catalog и параметры дублируются в нескольких switch/списках | ViewModel на вкладку, incremental observable updates, единый каталог эффектов |
| R17 / P2 | AudioFormatConverter пересчитывает каждый блок независимо: линейная интерполяция, округление длины, нет сохранения resampler phase между блоками | Потоковый ресемплер; тест произвольных packet sizes и 44.1/48/96 kHz |
| R18 / P2 | Ошибки ряда Save проглатываются, UI может сообщить успех после фактического провала сохранения | Typed result/error, единый error policy и несохранённое состояние в UI |
| R19 / P2 | AutostartService.RefreshAndRepairIfRegistered при запуске автоматически переписывает существующий Run-key на путь текущего EXE. Запуск portable/dev может изменить регистрацию установленной версии | Отделить read-only status от repair; исправление пути выполнять в явном install/update/enable-сценарии |

Возможные последствия R02: неправильный статус и сохранение playback-состояния; разные keyed one-shot могут оставаться в списке после фактического окончания virtual route. Повтор одного ключа заменяет предыдущий, поэтому утверждать бесконечное накопление от каждого повторного нажатия нельзя.

Microsoft отдельно указывает, что восстановление после повреждения состояния процесса через AccessViolationException не поддерживается: https://learn.microsoft.com/en-us/dotnet/api/system.accessviolationexception . Глобальный UnhandledException следует использовать для диагностики и корректного завершения, а не для безусловного `Handled=true`.

## 5. Размер поставки

Источник истины — имеющийся portable ZIP 12.5.1, а не текущий build 13.x:

| Артефакт | Размер |
|---|---:|
| Setup | 107,32 МиБ |
| Portable ZIP | 139,19 МиБ |
| Распакованное содержимое ZIP | 304,63 МиБ |
| deep_filter_ladspa.dll | 48,32 МиБ |
| Файлы с именами WPF/WindowsBase/WindowsFormsIntegration | 36,63 МиБ |
| Файлы WinForms/его design-сборок по имени | 28,38 МиБ |
| Satellite resources 13 культур | 15,53 МиБ |
| VB-CABLE ZIP + распакованный пакет | 4,57 МиБ |
| PDB | 0,21 МиБ |

Группы по имени — инвентаризация, не список файлов для ручного удаления. WinForms используется главным образом для tray, System.Drawing — для tray/превью; полный WindowsDesktop framework в self-contained поставке подтягивает значительно больше кода, чем собственный код VoiSee. Windows SDK projection DLL отдельно занимает 23,73 МиБ, WinUI native XAML — 14,39 МиБ. Отображение DLL на диске не означает, что весь файл одновременно находится в приватной RAM.

Предлагаемый порядок уменьшения:

1. Исследовать замену WinForms NotifyIcon на небольшой Windows tray adapter и NAudio metapackage на конкретные NAudio.Core/Wasapi/WinMM плюс Vorbis. System.Drawing для preview заменить только после проверки качества/стоимости альтернативы. Затем опубликовать заново без WindowsDesktop dependency и сравнить размер; не удалять DLL по догадке.
2. Ограничить satellite cultures реально поддерживаемыми языками; оценивать чистый publish и поведение fallback. Верхняя граница текущей группы — 15,53 МиБ, экономия будет меньше, если сохраняются несколько культур.
3. Устранить двойное включение VB-CABLE ZIP и распакованной копии; сохранить полный комплект INF/CAT/SYS рядом с setup. Это небольшая экономия и не должно ломать offline install.
4. По продуктовой политике рассмотреть optional DeepFilterNet component с проверкой версии/hash и явной offline full-поставкой. Уменьшение base на 48,32 МиБ не означает уменьшения полной установленной программы при выбранном DeepFilterNet.
5. Сравнить self-contained full и framework-dependent installer с bootstrap prerequisites. Во втором случае уменьшается пакет, но runtimes по-прежнему занимают место на компьютере и должны надёжно устанавливаться.
6. Не начинать с удаления PDB: текущая экономия всего 0,21 МиБ, а символы нужны для crash diagnostics; их можно хранить отдельно по build ID.

Включать PublishTrimmed/Native AOT как быстрый переключатель нельзя. У Microsoft есть ограничения trimming для WPF, WinForms и COM: https://learn.microsoft.com/dotnet/core/deploying/trimming/incompatibilities . Сначала убрать лишние зависимости и проверить native/WinRT/XAML/JSON пути; затем отдельный эксперимент с полным smoke на поддерживаемых Windows. Не смешивать это с первым этапом архитектурного переноса.

## 6. Целевая архитектура

Переписывать весь продукт одним изменением рискованно. Предлагается постепенно выделить модули, сохраняя UI и поведение 12.5.1. Не требуется сразу создавать стороннюю plugin ecosystem или отдельный процесс для каждой функции.

```text
VoiSee.App (WinUI Views + ViewModels + composition)
    → VoiSee.Application (сценарии и команды, состояние приложения)
        → VoiSee.Core (модели, контракты, схемы и правила)

VoiSee.Audio (engine, transports, DSP, buffers)
VoiSee.Infrastructure (persistence, Windows integration, files)
    → реализуют контракты Core/Application
```

Названия и количество csproj предварительные. Суть — направление зависимостей и владение состоянием:

- **Presentation:** отдельные страницы/ViewModels для SoundBoard, Voice Changer, Scenes, Media Bridge, Settings. Code-behind оставляет обработку pointer/drag/window interop. Слайдер не пишет JSON и не управляет WASAPI напрямую.
- **Application:** AudioSessionController, SoundboardService, SceneCoordinator, SettingsService, MediaBridgeController. Все команды start/stop/reconfigure сериализованы, результат и ошибка наблюдаемы.
- **Core:** stable IDs и immutable snapshots VoiceChain/Scene; versioned schemas и последовательные миграции. UI-компонентов и файлового I/O здесь нет.
- **Audio:** заранее собранный processing graph, каталог параметров эффектов, блоковая обработка Span<float>, заранее выделенная память. Новый эффект регистрируется через descriptor/factory, а не добавлением одинаковых switch во всём MainWindow. Поток обработки владеет состоянием DSP; новый settings snapshot подменяется на границе блока.
- **Infrastructure:** AtomicJsonStore с recoverable writes, MediaCatalog и bounded cache, HotkeyService, TrayService, DeviceService, bounded logging/crash reports.
- **Composition:** один явный владелец каждого IDisposable/worker, один application cancellation token, дочерние scopes для окна, движка, редактора и capture.

У движка необходимы состояния `Stopped → Starting → Running → Stopping`, плюс `Faulted/Reconnecting`. Повторный Stop безопасен; новый Start не конкурирует со старым Stop. Все запуски декодирования и захвата имеют operation ID, чтобы поздние результаты не восстанавливали уже отменённое состояние.

### Отдельный AudioHost

В репозитории уже есть его прототип, но главный путь 12.5.1 работает внутри UI. Изоляция движка могла бы защитить окно от native crash и позволить освобождать DeepFilterNet вместе с процессом. Цена — ещё один runtime-процесс, IPC, сложное восстановление и тестирование Discord screen-share маршрутов.

Сначала выделить `IAudioEngine` и устранить lifetime-ошибки, затем сравнить in-process и один AudioHost. Если AudioHost выбран, весь capture/DSP/mixing/render остаётся внутри него; через IPC идут команды и редкие telemetry snapshots. Не передавать каждую PCM-порцию через UI. Существующий AudioEngineClient с синхронными ожиданиями и poll каждые 40 мс нельзя подключать без переработки timeouts/cancellation/shutdown.

## 7. Безопасная последовательность работ после согласования обновлений

1. **Baseline и наблюдаемость:** ветка от b1829bb, неизменяемая копия пользовательских форматов, build/release ID, crash dumps, live profiling protocol и golden audio fixtures. Отделить версии 13.x, не переносить AI в архитектурный этап автоматически.
2. **Данные и lifetime:** R03–R11, отмена задач, owner объектов, state machine, атомарное хранение и миграции. Это защита до дальнейшего рефакторинга.
3. **Память и transport:** bounded cache/streaming, устранение scratch allocations, R02, limit voices, preallocated ring buffers; сравнение звука до/после.
4. **Модули приложения:** извлекать по одной области в service/ViewModel, начиная с уже стабилизированного управления движком и хранения; каждый шаг сохраняет существующий UI.
5. **DSP-каталог и state snapshots:** единые descriptors, независимый lifecycle эффектов; оптимизация по профилю без произвольной смены звучания.
6. **Поставка:** убрать лишние framework-зависимости, чистый publish, сравнить варианты установки. Проверить чистую Windows VM и обновление поверх 12.5.1.
7. **Длительная приёмка и release:** только после исправления регрессий и измерений на репрезентативном слабом ПК.

Каждый этап — отдельный reviewable change. Не объединять перенос UI, изменение DSP-математики, смену форматов и сокращение runtime в один большой коммит.

## 8. Критерии приёмки и следующий live-профиль

Численные бюджеты ниже — предлагаемые стартовые критерии, а не уже достигнутые характеристики:

- Cache: настраиваемый явный предел (начальный кандидат 64–128 МиБ); наличие 100 длинных треков в библиотеке не вызывает их полного декодирования при запуске.
- Audio allocations: целиться в 0 managed bytes/block steady-state у engine/mixer/queues; исключения и decoder-start измеряются отдельно.
- Deadline: измерять p50/p95/p99/max и underruns; p99 CPU-времени callback должен иметь большой запас относительно длительности блока. На эталонном ПК начальный ориентир — менее 25% block budget, затем подтвердить на слабом ПК.
- Сохранять полный микс и независимость Voice Monitor/SoundBoard/Media Bridge/mute; побитовое сравнение там, где алгоритм не менялся, допуск/слуховая оценка там, где изменён resampler.
- Soak: 60 минут смены сцен/пресетов, треков, тем, start/stop; затем extended 8-hour run. После прогрева не должно быть продолжающегося роста retained heap, private bytes, handles и threads при повторении одинакового набора действий. Working Set может колебаться из-за ОС; одного его графика недостаточно.
- Failure matrix: отсутствие микрофона/кабеля, hot unplug USB/BT, смена default device, sleep/resume, смена формата/частоты, конец процесса Media Bridge, закрытие во время async start/decode, read-only/full disk, повреждённый JSON/аудиофайл, 1000 tracks и большие сцены.
- Storage: принудительный сбой перед/во время commit не уничтожает предыдущий файл; ошибки записи видны пользователю.
- Release: чистый restore/build в CI с pinned dependencies; артефакт/символы с единым build ID; smoke чистой установки, обновления с 12.5.1 и удаления с сохранением user data.

Для фактического потребления всей программы требуется один фиксированный сценарий и исходная библиотека: запуск без engine; clean mic; RNNoise; DeepFilterNet; 1/8/32 звука; сцена; Media Bridge с превью/без; редактор длинного файла; трей. По каждому — steady-state 60–120 секунд и повторения, Working Set/Private Bytes/heap/allocations/GC/handles/threads, CPU нормализованный и в эквиваленте одного ядра, disk I/O, GPU video/copy/render и underruns. Затем те же сценарии после каждого этапа.

Официальные диагностические инструменты для managed-части: https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters и https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-highcpu . Native memory/GPU/driver effects требуют дополнительно Windows trace/профилировщика; одного dotnet-counters недостаточно.

## 9. Состояние после аудита

Найдены воспроизводимые проблемы, достаточные для начала архитектурной ветки, но утверждать, что найдены все возможные вылеты, нельзя. Самые большие подтверждённые выигрыши ожидаются от ограниченного PCM-кеша, микширования без временных массивов, безопасного сохранения и упорядоченного lifecycle; простой перенос методов из MainWindow по файлам этих проблем не исправит.

Production-код, пользовательские данные, ветки и установленные драйверы не менялись. Рефакторинг и создание новой ветки оставлены до объяснения пользователем желаемого порядка обновлений.
